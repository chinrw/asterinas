A Nix dev shell for Asterinas

An opt-in alternative to the Docker development environment, pinned component-for-component to what the Dockerfiles build. Docker stays canonical; nothing about the existing workflow changes.

PR #3548 open · CI green 9 commits 4-stage roadmap below

Why a Nix dev shell

Nix is already load-bearing in this repository: the test initramfs is built with nix-build, the AsterNixOS distribution under distro/ is a NixOS configuration, CI publishes to a Cachix cache, and the development Docker image installs Nix inside the container to drive those builds. The development environment was the one piece not yet expressed in Nix. The flake closes that gap — pinning the exact nixpkgs commit the repository already uses twice — and implements the development-shell half of #2642. It is also a concrete step toward developing Asterinas on Asterinas: AsterNixOS guests already run the Nix-provisioned development tools, direnv included.

  • Granular fetching. Docker ships one ~3 GB all-in-one image; Nix resolves individual store paths — a lint-only task pulls a fraction of the closure, macOS never downloads the Linux boot stack, and nothing is fetched twice.
  • Editor integration. The toolchain and a matching rust-analyzer derive from rust-toolchain.toml, with VDSO_LIBRARY_DIR exported — an editor started inside the shell checks the kernel crates out of the box.
  • One prerequisite. Just the Nix package manager — one installer command on any distro or macOS, preinstalled on NixOS; no daemon, no privileged container, and on macOS no Linux-VM detour.
  • Reproducibility as security. Every input is content-addressed and hash-pinned: a tampered dependency fails closed, and bit-identical builds can be verified independently.
The design constraint: no drift. The flake packages the boot stack at exactly the versions the Dockerfiles build, every pin carries a comment naming its Dockerfile counterpart, and a sync-check script (first wave, below) turns any future divergence into a CI failure.

The shell exports VDSO_LIBRARY_DIR and OVMF_DIR when not already set, so nix develop followed by make run_kernel needs no manual setup. A tracked .envrc adds direnv support — approval is bound to the file's content hash, so nothing executes without an explicit direnv allow. Changes to existing files are deliberately small: tools/qemu_args.sh reads the firmware directory from OVMF_DIR with the default unchanged, so Docker is unaffected. The branch also carries the flake’s CI workflow: evaluation across all systems, builds of the four packages, and an isolated dev-shell smoke test.

How it was validated

  • nix flake check --all-systems, plus the repo's nixfmt and typos gates extended over the new files.
  • Boot smoke (make run_kernel AUTO_TEST=boot) on x86_64 Linux with KVM — repeated under nix develop --ignore-environment to rule out anything leaking in from the host.
  • All four packages built and inspected on x86_64-linux and aarch64-linux; on aarch64 the GRUB userland tools are a native build while the EFI modules stay x86_64.
  • On an Apple-silicon Mac: clippy, the ostd cross-build, typos and mdbook work; the boot-stack packages are correctly Linux-only.
  • Outside the shell, ./tools/qemu_args.sh still emits the original /root/ovmf/release paths.

Known gaps, stated up front: cargo osdk new scaffolds still hardcode the Docker firmware paths (fix in the first wave, below); the gvisor tests need the Docker image's prebuilt binaries; and some nixpkgs-provided lint tools lag the versions Docker pins, so make check in Docker remains the CI reference.

Try it

# One-time setup: enable flakes (an experimental feature of Nix) by adding
# this line to /etc/nix/nix.conf or ~/.config/nix/nix.conf:
experimental-features = nix-command flakes

# From the repository root, one command prepares the complete development
# environment — pinned Rust toolchain + rust-analyzer, QEMU, GRUB, OVMF,
# klint, and the host tools the Docker image provides:
nix develop

# The usual targets then work without further setup:
make kernel
make run_kernel

# Or build / run a single component without entering the shell (Linux only):
nix build .#qemu               # also .#grub, .#ovmf, .#klint
nix run .#qemu -- --version    # runs the packaged qemu-system-x86_64

Flakes and the unified nix CLI are opt-in Nix features; the NixOS wiki page on flakes covers enabling them per-user or system-wide.

How it fits together

Bands are rollout stages, top to bottom. Arrows mark the hard orderings inside a stage; the bottom Stage 3 row is order-independent, and the kernel-packaging item is what Stage 4 consumes.

The through-line guarantee: Nix runs inside the container during the build, so a host without Nix produces the same image with a plain docker build — Nix is an implementation detail of the image, never a prerequisite for building it.

Where maintainer input would help most

  1. Binary cache: reuse the existing aster-nixos-dev Cachix (zero new credentials) or provision a flake-specific one?
  2. Docs placement: is a Book page under Before You Contribute the right home, or should the READMEs stay the only entry points?
  3. Version pins: is a sync-check script enough for now, or is there appetite for a single-source versions file that both the Dockerfiles and the flake read?
  4. nixpkgs cadence: the flake pins the same commit as the Docker nix layer and the initramfs package set — should the three always move together?
